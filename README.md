# Bingr-beheer

Het beheer-dashboard van **Bingr**, op **https://beheer.bingr.online**. Het dashboard stond eerder op `bingr.online/admindashboard` in de repo bingr-website.

**Deze repo is openbaar.** Iedereen kan de code, de commits en de logs van de workflows lezen. Daarom:

- **Geen geheimen**: wachtwoorden, tokens, SMTP-gegevens, `service_role`-sleutels en dergelijke alleen als GitHub-secrets (zie hieronder), nooit in een bestand, commit, issue of log. Wel toegestaan: de publieke Supabase-URL en de publishable key (`web/config.js`, `ios/…/AdminAPI.swift`) en de project-ref die daarin staat.
- **Geen persoonsgegevens**: geen e-mailadressen, namen, account-id's, tickets of exports van gebruikers, ook niet als testdata of in screenshots.
- **Geen logs met servergegevens**: workflows en scripts schrijven geen secrets, interne adressen, FTP-mappen, volledige serverantwoorden met gebruikersgegevens of stacktraces met configuratie naar het log; zet zulke stappen op een korte melding (`::notice::` / `::warning::`) zonder waarden.
- De beveiliging hangt niet af van geheimhouding van de code: alles achter het inloggen loopt via de functie `admin` met een ondertekend token.

- `web/` — het dashboard zelf (statische HTML/JS/CSS, geen build-stap): overzicht, insights, omzet, gebruikers, pushmeldingen, nieuwsbrief, supporttickets, status en downloads. Navigatie alleen via het hamburgermenu rechtsboven (op elke breedte; badge = ongelezen in Support). Alles staat erin (`config.js` met de publieke Supabase-URL en publishable key, favicon). `robots.txt` blokkeert alles en de pagina heeft `noindex`.
- `ios/` — de native app **BingrBeheer** (iOS/iPadOS 17+, en via Mac Catalyst macOS 14+) met dezelfde onderdelen als het web-dashboard; zie *iOS-app* en *Mac-app* hieronder.
- `supabase/functions/admin` — de Supabase Edge Function `admin` waar het dashboard mee praat (inloggen, statistieken, gebruikers, accountmails, de tab Pushmeldingen via de functie `push`, de tab Nieuwsbrief via de functie `newsletter`, de pushmeldingen van de Beheer-app zelf, de tab Status via de functie `status` en de tab Support via de functie `support`). `supabase/functions/_shared/mail.ts` is een kopie van die in iptv-ios-appletv.

Wat er **niet** in staat: het databaseschema (ook de beheertabellen), de functies `device-auth`, `web-proxy`, `status` en `push`, en de statusplanning. Die staan in de openbare repo [LRvdLinden/iptv-ios-appletv](https://github.com/LRvdLinden/iptv-ios-appletv) (`supabase/`, workflow *Backend*). De afmeldpagina `bingr.online/unsubscribe/` staat op de gewone site en roept alleen de actie `unsubscribe` van `admin` aan; dat is het enige wat bingr.online mag.

Beveiliging (build 97):

- Het token (12 uur) bevat geen inlognaam meer, wel een **tokenversie** (tabel `admin_token_state`); elk verzoek controleert die. **Overal uitloggen** (Instellingen en het menu rechtsboven, web en app; actie `logout_all`) verhoogt de versie: alle sessies vervallen meteen, en alle apparaten worden afgemeld voor de pushmeldingen van de Beheer-app (`admin_push_devices` leeg). Een ander `BINGR_ADMIN_PASSWORD` trekt de sessies ook in.
- Limieten per IP: na inloggen 300 verzoeken per minuut, afmelden (`unsubscribe`) 20 per 10 minuten (one-click vanaf mailservers 200 per 10 minuten).
- Het logboek (`admin_audit`) bevat ook inzage van persoonsgegevens (`user_view`, `users_search`, `user_email_view`, `support_view`: alleen actie en id/nummer, geen inhoud; `user_set_name` zonder de naam zelf), geblokkeerde inlogpogingen (`login_locked`) en mislukte acties (`<actie>_failed` met foutcode).
- Het dashboard heeft een strikte Content-Security-Policy (`web/.htaccess`, ook als meta in `index.html`): geen inline scripts of styles, alleen verbinding met de eigen Supabase-URL.
- De GitHub Actions staan vast op een commit-SHA en de Supabase CLI op een vaste versie; de unittests blokkeren de deploy.

Wijzigingen in deze repo komen **nooit** in de openbare changelog (`docs/changelog.json`), niet op bingr.online en niet in de release-notities.

## Dashboard (tab Overzicht)

Het overzicht is een instelbaar dashboard met widgets, op het web en in de app (zelfde model). Zonder eigen indeling toont het de standaardindeling (lijkt op het vroegere vaste overzicht): tien kengetallen (gebruikers, nieuw, actief vandaag/30 dagen, apparaten, kijkt nu, open tickets, geblokkeerd, Gratis, Lifetime), sinds build 134 ook geweigerde registraties en verwijderde onbevestigde accounts, servicestatus, drie Insights-grafieken (accounts 30 dagen, streams 7 dagen, pushmeldingen 30 dagen; zie *Insights*), apparaten per platform en app-versies.

- **Wijzig** zet de wijzigmodus aan. Per widget: grootte **S** (1×1), **M** (2×1) of **L** (2×2), verplaatsen (web: slepen met de muis, of de pijlknoppen *naar voren* / *naar achteren* met het toetsenbord; app: lang drukken en slepen, de pijlen, of de grepen in *Widgets*), **instellen** (schuifjes: getoonde gegevens) en **verbergen**. **Widget toevoegen** (web) / **Widgets** (app) toont verborgen widgets (tonen of verwijderen) en de galerij. **Standaard herstellen** zet alles terug; *Standaard voor deze widget* doet dat voor één widget.
- Raster: web 4 kolommen, 2 onder 1000 px, 1 kolom op telefoonbreedte (≤ 600 px); app 4 kolommen op de iPad (regular), 2 op de iPhone. Widgets vullen de eerste vrije plek (geen gaten; web `grid-auto-flow: row dense`).
- Gegevens: `insights` (per Insights-widget, eigen periode; 1 minuut in het geheugen), `stats` (altijd), `support_counts` (elke 2 minuten, zoals de badge), `status` met `op: overview` (alleen als er een zichtbare widget Servicestatus of *Nu actieve apparaten* is), `push_history` (eerste bladzijde, alleen met een zichtbare widget Laatste pushmeldingen), `push_subscribers` (alleen met een zichtbare widget Pushabonnees) en `newsletter_status` (alleen met een zichtbare widget Nieuwsbrief).
- Opslag per apparaat: web in `localStorage` onder `bingrAdmin.dashboard`, app in `UserDefaults` onder `dashboardLayout` (JSON-tekst). Niet op de server en niet gedeeld tussen apparaten; doordat beide hetzelfde JSON gebruiken, kan synchroniseren later via een serveractie.

### JSON-model (versie 1)

```json
{
  "version": 1,
  "widgets": [
    { "id": "users", "type": "metric", "size": "s", "hidden": false, "options": { "metric": "users_total" } },
    { "id": "chart_new", "type": "daily_chart", "size": "l", "hidden": false, "options": { "series": "new_users", "days": 30, "display": "chart" } }
  ]
}
```

- `version`: altijd `1`. Een andere versie, geen geldige JSON of geen enkele geldige widget = standaardindeling.
- `widgets`: volgorde = plaats op het dashboard; max. 40. `id`: `[A-Za-z0-9_-]{1,40}`, uniek (ongeldig of dubbel = nieuw id `<type>_<n>`). Een widget met onbekend `type` valt weg (de rest blijft). `size`: `s`, `m` of `l`, alleen de maten van het type (anders de standaardmaat). `hidden`: verborgen maar bewaard (standaard `false`). `options`: alleen de sleutels hieronder; een ontbrekende of ongeldige waarde krijgt de standaard (**vet**).

| `type` | maten (standaard) | `options` |
| --- | --- | --- |
| `metric` (Kengetal) | s, m (**s**) | `metric`: **`users_total`**, `users_new_7d`, `active_today`, `active_30d`, `devices`, `watching_now`, `blocked`, `plan_free`, `plan_lifetime`, `plan_custom`, `opted_out`, `purchases_paid`, `revenue_cents`, `signups_rejected` (build 134: registraties geweigerd in 24 uur, per reden limiet/wegwerp/naam en 7 dagen; `stats.signup_guard`), `unconfirmed_deleted` (onbevestigde accounts verwijderd in 7 dagen en 24 uur) |
| `insights` (Grafiek, zie *Insights*) | s, m, l (**l**; op het raster M = 2×2 en L = 2×3) | `insight`: **`accounts`**, `signins`, `streams`, `push`, `support`; `period`: `hour`, `day`, `week`, `month`, `year`, `24h`, `7d`, **`30d`** (ook op de widget zelf te kiezen); `display`: **`auto`**, `line`, `bar`, `number` (S toont altijd het getal); `events`: **true** (storingen/onderhoud als banden); `off`: series die via de legenda uit staan (**leeg**). Het vroegere type `daily_chart` (Per dag) wordt bij het lezen omgezet: `series` signins → `signins`, anders `accounts` (met de andere serie in `off`), `days` 7 → `7d`, anders `30d`, `display` number blijft `number` |
| `platforms` (Apparaten per platform) | m, l (**l**) | `source`: **`30d`** (stats) of `live` (laatste 15 min, uit `status`); `platforms`: lijst platformnamen zoals in de gegevens (**leeg = alle**) |
| `versions` (App-versies) | m, l (**l**) | `platforms`: als hierboven |
| `plans` (Abonnementen) | s, m, l (**m**) | `plans`: deelverzameling van **`free`, `lifetime`, `custom`** (niet leeg) |
| `support` (Supporttickets) | s, m, l (**s**) | `statuses`: deelverzameling van `new`, `open`, `pending`, `resolved`, `closed` (**new, open, pending**; niet leeg); `display`: **`number`**, `list` |
| `status` (Servicestatus) | s, m, l (**m**) | `show_incidents`: **true**; `show_notices`: **true** |
| `announcements` (Laatste pushmeldingen) | m, l (**l**) | `count`: **3**, 5. Toont sinds build 14 van de app de pushgeschiedenis (`push_history`: soort, titel, datum, aantal verstuurd); het type-id blijft `announcements`, zodat bewaarde indelingen blijven werken. `only_active` bestaat niet meer en valt weg |
| `push_subscribers` (Pushabonnees) | s, m, l (**m**) | `push_platforms`: deelverzameling van **`ios`, `ipados`, `macos`, `android`, `web`** (niet leeg; telt alleen de apparaten, accounts altijd alle platforms); `show_new`: **true** (nieuwe accounts in 7 dagen) |
| `newsletter` (Nieuwsbrief) | s, m (**s**) | `show_langs`: **true** (NL/EN apart). Abonnees = `recipients.total` van `newsletter_status` (geabonneerd met bevestigd e-mailadres), ten opzichte van alle leden (`stats.total_users`); ook of de verzending aan staat. Niet in de standaardindeling; via de galerij toevoegen |

Code: web in `web/admin.js` (blok *overzicht: instelbaar widget-dashboard*, `normLayout`), app in `ios/BingrBeheer/Models/Dashboard.swift` (`DashLayout.normalized()`) en `ios/BingrBeheer/Views/Overview/`. Houd beide gelijk als je een type of optie toevoegt (en verhoog `version` alleen als oude indelingen niet meer kloppen). Niets hiervan komt in de changelog.

## Insights (grafieken zoals Homey Insights)

Grafieken door de tijd, op het web en in de app, in twee vormen: de widget **Grafiek (Insights)** op het overzicht en de tab **Insights** (bronnen aanvinken en vergelijken). Alles in Nederlandse tijd (Europe/Amsterdam).

- **Bronnen (metrics) en series** (kleur vast per serie, categorisch palet; ook leesbaar bij kleurenblindheid):
  | metric | series | bron (iptv-ios-appletv, `supabase/schema.sql`) |
  | --- | --- | --- |
  | `accounts` | nieuwe accounts; actieve accounts (gemiddelde per dag, alleen per dag of week) | `auth.users.created_at`; `account_logins` (één rij per account per dag, 400 dagen) |
  | `signins` | inlogs | `auth.audit_log_entries` (action `login`), als die er is |
  | `streams` | live tv, films, series (gestarte streams) | per 5 min/uur: `account_watch_log` (8 dagen); per dag/week: `account_watch_stats.plays` (400 dagen) |
  | `push` | verstuurd, mislukt (failed + invalid) | `push_deliveries` (30 dagen), daarvoor de tellers van `push_messages` (400 dagen; herinneringen 3 dagen) |
  | `support` | nieuwe tickets, gesloten | `support_tickets.created_at` / `closed_at` |
- **Periodes en resolutie** (past zich aan, zoals Homey): Uur = per 5 minuten; Dag = per uur (23/25 uur bij de klokwissel); Week (ma–zo) en 7 dagen = per uur, of per dag als de metric actieve accounts heeft of de streams ouder zijn dan 8 dagen; Maand en 30 dagen = per dag; Jaar = per week (eerste en laatste week korter); 24 uur = per uur. **‹ ›** bladert naar de vorige/volgende periode (tot ca. 3 jaar terug), **Nu** gaat terug. Toekomstige tijdvakken blijven leeg (de lijn stopt bij nu).
- **Samenvatting** per serie: totaal (of gemiddelde per dag), verandering t.o.v. hetzelfde stuk van de vorige periode (▲/▼ met kleur: groen = goed, voor *Mislukt* omgekeerd; geen vergelijking als een deel van de vorige periode niet meer bewaard is), en op L / in de tab ook min, max, gemiddelde en de waarde van nu. De samenvattingsknoppen zijn ook de **legenda**: tik om een serie aan/uit te zetten (minstens één blijft zichtbaar; onthouden).
- **Grafiek**: vloeiende lijn (monotoon) met zacht kleurverloop, of staven (automatisch voor pushmeldingen en tickets per dag of week; per widget te kiezen), dunne rasterlijnen, slimme tijdlabels. **Crosshair** met tooltip (tijdvak + waarde per serie) en een punt op de lijn: muis, vinger (slepen) of pijltjestoetsen (web). Storingen van publieke monitors en gepland onderhoud van de statuspagina staan als **banden** op de tijdas (naam in de tooltip; geen lijn). Lege periode: *Geen gegevens in deze periode*. Laden met een skelet; bij een andere periode blijft de oude grafiek vervaagd staan tot de nieuwe er is.
- **Tab Insights**: links de bronnen met vinkjes (op telefoonbreedte als knoppen; in de app op de iPhone via *Bronnen*), één gedeelde periode bovenaan, de grafieken onder elkaar met een **gedeelde crosshair** (hover op de ene grafiek toont hetzelfde tijdstip op alle). **Download CSV** (web: bestand; app: delen) met de zichtbare reeksen: begin, einde en de aantallen per tijdvak (`;`, decimale komma), nooit persoonsgegevens. Keuze onthouden: web `localStorage` `bingrAdmin.insights`, app `UserDefaults` `insightsPage` (`{sources, period, events, off}`). Op de iPhone staat Insights in het menu rechtsboven (blad); op iPad en Mac in de zijbalk (Mac: ⌘2).
- **Actie** `insights {metric, period, offset (0, -1, …), events?}` → `{step, edges, now_index, has_prev, has_next, series:[{key, label, agg, available, values, prev_values, summary:{total, avg, min, max, last, prev, change_pct}}], events?:[{kind, name, from, to}]}`. De functie rekent de grenzen van de tijdvakken uit en vraagt de vorige periode in dezelfde aanvraag mee; de database telt alleen per tijdvak (`bingr_admin_insights(p_metric, p_edges, p_daily)` en `bingr_admin_insights_events(p_from, p_to)` in iptv-ios-appletv, security definer, vaste `search_path`, alleen `service_role`; het hulpje `bingr_insights_bin` is voor niemand aan te roepen). Zonder bijgewerkt schema: `insights_not_configured` (workflow *Backend* in iptv-ios-appletv draaien). Code en tests: `supabase/functions/admin/insights.ts`, `insights_test.ts` (blokkeren de deploy); web `web/admin.js` (blokken *grafieken zoals Homey Insights* en *tab Insights*); app `ios/BingrBeheer/Models/Insights.swift` en `Views/Insights/`. Niets hiervan komt in de changelog.

## Tab Omzet

Lifetime-aankopen via Stripe, op het web en in de app (onderdeel *Omzet*; op de iPhone via het menu), met dezelfde bediening als Insights: periode (dag, week, maand, jaar, 7 of 30 dagen; jaar per maand of per week, week per dag of per uur), bladeren met ‹ › en Nu, crosshair met tooltip, series aan/uit.

- **Tegels:** deze maand, vorige maand, dit jaar en totaal: bruto, netto, opbrengst en aantal aankopen.
- **Grafieken:** omzet (bruto incl. btw, netto excl. btw, opbrengst; lijnen of staven) en aankopen/terugbetalingen per tijdvak.
- **Van bruto naar opbrengst** (deze en vorige periode): aankopen, bruto, btw, netto, Stripe-kosten, terugbetaald/chargebacks (excl. btw) en netto opbrengst = netto − Stripe-kosten − terugbetalingen excl. btw. Aankopen tellen op de betaaldatum, terugbetalingen op hun eigen datum.
- **Verdeling** per betaalmethode (iDEAL, kaart, Apple Pay, Bancontact, …) en per land (alleen landcode).
- **Btw:** met Stripe Tax (`STRIPE_AUTOMATIC_TAX`) de werkelijke `total_details.amount_tax` per aankoop, anders berekend: bedragen zijn incl. btw, btw = bruto × tarief / (100 + tarief); tarief standaard 21% (NL), in te stellen in de tab (`app_settings.revenue_vat`). De tab zegt welk uitgangspunt geldt en dat het een indicatie is, geen aangifte.
- **Stripe-kosten:** vult de webhook (`stripe-webhook` in iptv-ios-appletv) bij betaling of bij `charge.updated`; ontbreken ze nog, dan **Kosten ophalen bij Stripe** (actie `revenue_backfill`, met het function-secret `STRIPE_SECRET_KEY`).
- **Live of test:** standaard de aankopen van de modus van `STRIPE_SECRET_KEY` (`cs_live_…` / `cs_test_…`), te wisselen naar live, test of beide.
- **CSV** (actie `revenue_export`): per aankoop en terugbetaling alleen datum, soort, bedrag, btw, kosten, netto, methode en land; geen e-mail, naam, account of Stripe-id.
- Zonder aankopen (of zonder `STRIPE_SECRET_KEY`): “Nog geen aankopen”. Schema en SQL-functies (`bingr_admin_revenue`, `bingr_admin_revenue_rows`, tabel `billing_refunds`) staan in iptv-ios-appletv (`supabase/schema.sql`, workflow *Backend*); zie `docs/ACCOUNT.md` daar. Logica en tests: `supabase/functions/admin/revenue.ts` / `revenue_test.ts`.

## Gebruikers: blokkeren en verwijderen

Accounts hebben een voor- en achternaam (Supabase `user_metadata` `first_name` / `last_name`, gevraagd bij het aanmelden). De lijst toont de naam boven het gemaskeerde e-mailadres; zoeken werkt op het begin van het e-mailadres en op het begin van een woord in de naam (voornaam, achternaam of "voornaam achternaam"; `bingr_admin_users` in iptv-ios-appletv). In de lade (web en app):

- **Naam → Wijzig**: voor- en achternaam (actie `user_set_name`, opgeschoond, max. 50 tekens elk, leeg = geen naam; de rest van de metadata blijft staan). De beheermails (blokkeren, opheffen en verwijderen) beginnen met *Hoi <voornaam>,* (*Hi <first name>,*) als de voornaam bekend is.
- **Oog naast het e-mailadres**: toont het volledige adres (actie `user_email`, in het logboek als `user_email_view` zonder het adres); nog een keer klikken verbergt het weer.

- **Blokkeren…**: reden (de klant ziet hem), duur (1 dag, 7 dagen, 30 dagen, onbepaald of een eigen datum) en *Klant mailen*. **Nieuwsbrief per account** (lade van een account, web en app; lijst: chip *Geen nieuwsbrief*): bron is `account_email_prefs.newsletter_opt_out` (schema in iptv-ios-appletv). De schakelaar zet alleen `newsletter_opt_out` (actie `user_newsletter_set {id, subscribed}`, upsert met de service role; in `admin_audit` alleen `subscribed`, nooit het e-mailadres). **Keuze:** heeft de klant alle mail van Bingr uitgezet (`email_opt_out`), dan toont het beheer *Geen e-mail (alles uitgezet)* zonder schakelaar en weigert de functie aanzetten (409 `email_opted_out`): die afmelding is van de klant zelf en het beheer zet hem niet terug. ### Antwoorden per e-mail (inbox-import)

De functie `support` haalt elke 2 minuten nieuwe mails uit de INBOX van support@bingr.online (IMAP over TLS, pg_cron-taak `bingr-support-inbox`, ingesteld door de workflow *Backend* in iptv-ios-appletv) en zet ze in het ticket:

- **Klant antwoordt op een ticketmail** (onderwerp `[#1007]` of een antwoord op onze Message-ID) vanaf het adres van het ticket: bericht van de klant (label *✉ per e-mail*), status weer *In behandeling*, ticket ongelezen. Een ander adres met hetzelfde ticketnummer wordt geweigerd en blijft ongelezen in de mailbox staan.
- **Jij antwoordt vanuit je mailbox** op een melding (*Nieuw ticket* / *Reactie van klant*): de Reply-To van die meldingen is support@ zelf, dus je antwoord komt via de import in het ticket en gaat als gebrande mail naar de klant. Schrijf boven de regel *-- Antwoord boven deze lijn --*; citaten en handtekeningen worden weggeknipt.

Verwerkte mails worden gelezen en naar de map **Bingr-verwerkt** verplaatst als die bestaat (maak hem zelf aan in de mailbox). Bijlagen worden niet overgenomen (alleen een regel met de naam).

Boven de ticketlijst staat de status van de import (laatste ronde, fout, *IMAP niet ingesteld*), een knop **Nu ophalen** en het logboek van de laatste mails. Zonder `BINGR_IMAP_*` blijft alles zoals vroeger (Reply-To van meldingen = de klant).

## Downloads (buildpakketten)

De buildpakketten van Bingr (Android/Android TV-APK, Android App Bundle `.aab` voor Google Play, Samsung TV-`.wgt`, Windows-installer `.exe`, Apple Xcode-project) en van BingrBeheer (Xcode-project) staan **niet** op GitHub: niet in een repo, niet als release en niet als onversleuteld artefact. Ze staan op de server van beheer.bingr.online in de afgesloten map `builds/` (`web/builds/.htaccess` weigert elke rechtstreekse aanvraag), met `builds/manifest.json` (per platform versie, build, bestand, grootte, SHA-256, datum, `uploaded_at` (moment van plaatsen door *Builds*, UTC ISO 8601; blijft ook in `history` staan), notities en de vorige builds die nog op de server staan). Downloads toont `uploaded_at` als datum en tijd in NL-tijd (bv. *17 okt 2026, 08:02*); oudere builds zonder dat veld tonen alleen `date`.

- **Workflow *Builds*** zet de pakketten (versleuteld aangeleverd door de bouwworkflows), het manifest en `builds/key.php` op de server, en zet dezelfde sleutel als function-secret **`BINGR_BUILDS_KEY`** (64 hex-tekens) in Supabase. Hier hoeft niets voor; de workflow *Admin-functie* zet of verwijdert die sleutel niet.
- **Aanleveren via de privé inbox-repo (H3):** de bouwworkflows van iptv-ios-appletv, bingr-android en bingr-windows versleutelen hun pakket met `tools/seal_build.sh` (anoniem gekloond uit deze openbare repo, samen met de publieke sleutel `builds.pub.pem`) en pushen het naar de branch `inbox-<platform>` van de **privé** repo `LRvdLinden/bingr-inbox`, met het secret `BINGR_INBOX_TOKEN` (alleen schrijfrechten op die repo; het token gaat als kopregel mee, nooit in een URL). Zonder dat secret leveren ze niets aan (met een waarschuwing) en vallen ze niet terug op een ander token. *Builds* draait elke 15 minuten (stopt meteen als er niets klaarstaat), haalt de pakketten daar op met `BINGR_INBOX_READ_TOKEN` en verwijdert de branch. Zo heeft geen andere repo nog schrijfrechten op deze openbare repo, waarmee iemand het dashboard of de functie `admin` zou kunnen vervangen. De Beheer-app (*Beheer-app*, `build-ios.yml`) levert met het eigen `GITHUB_TOKEN` aan op `inbox-beheer` van deze repo zelf en start *Builds* meteen; `seal_build.sh` weigert andere platforms naar bingr-beheer. Inbox-branches die nog in deze repo staan (van vóór de overgang) verwerkt *Builds* ook en verwijdert ze daarna.
- **Eenmalig instellen (eigenaar):**
  1. Maak op GitHub de **privé** repo `LRvdLinden/bingr-inbox` (leeg, zonder README is prima; geen Actions nodig).
  2. Maak een fine-grained token *Bingr inbox schrijven* (*Settings → Developer settings → Fine-grained tokens*): Resource owner LRvdLinden, *Only select repositories* = `bingr-inbox`, *Repository permissions → Contents: Read and write* (verder niets), met een vervaldatum. Zet het als secret **`BINGR_INBOX_TOKEN`** in **iptv-ios-appletv**, **bingr-android** en **bingr-windows** (het token mag voor alle drie hetzelfde zijn; het geeft alleen schrijfrechten op bingr-inbox).
  3. Maak een tweede fine-grained token *Bingr inbox verwerken*: alleen `bingr-inbox`, *Contents: Read and write*. Zet het als secret **`BINGR_INBOX_READ_TOKEN`** in **bingr-beheer**.
  4. Verwijder het secret **`BINGR_BEHEER_TOKEN`** uit iptv-ios-appletv en bingr-android, en **trek het token zelf in** (*Fine-grained tokens* → het token met schrijfrechten op bingr-beheer → *Delete*). Controleer in *Settings → Collaborators* en *Deploy keys* van bingr-beheer dat er geen andere schrijftoegang meer is dan jijzelf.
  5. Start in bingr-beheer *Actions → Builds → Run workflow* (controle: geen waarschuwing over `BINGR_INBOX_READ_TOKEN`), en daarna een build in iptv-ios-appletv of bingr-android (*Run workflow*): binnen 15 minuten staat hij in de tab Downloads.
- **Ondertekende buildpakketten (security M4):** elke aanleverende repo tekent zijn pakket met een eigen Ed25519-sleutel: het secret **`BINGR_BUILD_SIGN_KEY`** in **iptv-ios-appletv** (platform apple), **bingr-android** (android, android-aab, tizen) en **bingr-windows** (windows); `seal_build.sh` zet de handtekening (`meta.sig`) over `meta.json` (platform, build, versie, bestand, sha256, grootte, repo, commit; `tools/build_sig.py`). De **openbare** sleutels staan in `tools/signers/<repo>.pub.pem`; welke repo welk platform mag aanleveren staat in `tools/build_sig.py` (SIGNERS). *Builds* controleert vóór het plaatsen (`builds_verify` in `tools/builds_process.sh`): een ongeldige handtekening of een pakket van de verkeerde repo wordt **altijd** geweigerd (`::warning::`); zonder handtekening of zonder openbare sleutel alleen als de repository-variabele **`BUILDS_REQUIRE_SIGNATURE`** op `true` staat, anders aangenomen met een waarschuwing (overgang). De Beheer-app (platform beheer) komt alleen uit deze repo zelf en nooit uit de inbox-repo. Sleutels maken (lokaal, met `gh` ingelogd; de privésleutel gaat alleen naar het secret en wordt daarna gewist, de openbare sleutel komt in deze repo):
  `for r in iptv-ios-appletv bingr-android bingr-windows; do openssl genpkey -algorithm ed25519 -out /tmp/bingr-sign.pem && gh secret set BINGR_BUILD_SIGN_KEY -R LRvdLinden/$r < /tmp/bingr-sign.pem && gh api -X PUT repos/LRvdLinden/bingr-beheer/contents/tools/signers/$r.pub.pem -f message="Openbare ondertekensleutel $r (M4)" -f content="$(openssl pkey -in /tmp/bingr-sign.pem -pubout | base64 | tr -d '\n')"; rm -f /tmp/bingr-sign.pem; done`
  Eén repo opnieuw (bijv. als `seal_build.sh` meldt dat de sleutel niet past; het bestaande bestand overschrijven kan alleen met zijn `sha`): `r=bingr-windows; openssl genpkey -algorithm ed25519 -out /tmp/bingr-sign.pem && gh secret set BINGR_BUILD_SIGN_KEY -R LRvdLinden/$r < /tmp/bingr-sign.pem && gh api -X PUT repos/LRvdLinden/bingr-beheer/contents/tools/signers/$r.pub.pem -f message="Openbare ondertekensleutel $r (M4)" -f sha="$(gh api repos/LRvdLinden/bingr-beheer/contents/tools/signers/$r.pub.pem --jq .sha)" -f content="$(openssl pkey -in /tmp/bingr-sign.pem -pubout | base64 | tr -d '\n')"; rm -f /tmp/bingr-sign.pem` (op macOS met OpenSSL 3, bijv. `$(brew --prefix openssl@3)/bin/openssl`; LibreSSL kent geen Ed25519).
  `seal_build.sh` tekent met OpenSSL 3 (op macOS Homebrew `openssl@3`, want `/usr/bin/openssl` is LibreSSL) of anders python `cryptography`, over de bytes van `build_sig.py msg` (altijd LF, ook op Windows), en controleert de handtekening meteen met `tools/signers/<repo>.pub.pem`: lukt tekenen niet of past de sleutel niet, dan `::error::` met alleen de vingerafdrukken van de openbare sleutels en geen aanlevering.
  Daarna een build in elk van de drie repo's starten; geeft *Builds* bij alle platforms "handtekening … klopt", zet dan in bingr-beheer *Settings → Secrets and variables → Actions → Variables* `BUILDS_REQUIRE_SIGNATURE` = `true`.
- **Openbare testversie (Android):** `https://beheer.bingr.online/dl.php?app=android` levert zonder token alleen de **nieuwste Android-APK** uit het manifest (knop *Testversie downloaden* op bingr.online). Andere platforms (ook de App Bundle), oudere builds en het manifest blijven afgeschermd.
- **Openbare testversie (Windows):** `https://beheer.bingr.online/dl.php?app=windows` (en `https://bingr.online/windows`, knop *Download voor Windows* op bingr.online) levert zonder token alleen de **nieuwste Windows-installer** (`.exe`, met Range om te hervatten). ### Beheer-app: pushmeldingen

Sinds build 14 krijgt de app BingrBeheer (iPhone, iPad en Mac) zelf systeem-pushmeldingen via APNs (topic `nl.lrvdlinden.bingr.beheer`): **nieuwe tickets**, **nieuwe antwoorden** van klanten, **nieuwe builds** in Downloads en **statuswijzigingen**. Het web-dashboard krijgt geen push.

- **Versturen** doet de cron van de functie `push` in iptv-ios-appletv (niet deze repo). Hij leest de tabel `admin_push_devices` (`device_id`, `token` = APNs-devicetoken in hex, `platform` `ios`/`ipados`/`macos`, `sandbox`, `prefs` `{tickets, replies, builds, status}` (ontbrekende soorten, zoals `purchases` en `mailings`, staan aan), `app_build`, `last_error`) en stuurt `{aps: {alert: {title, body}, sound, "thread-id": kind}, kind, url}` met `kind` = `ticket` / `reply` / `build` / `status` / `purchase` / `mailing` (eigen mailing klaar: *Mailing verstuurd (x ontvangers)*, `bingrbeheer://newsletter`) en `url` = `bingrbeheer://support/<nummer>`, `bingrbeheer://downloads` of `bingrbeheer://status`.
- **Functie `admin`** (`admin_push.ts`, tests in `admin_push_test.ts`; service role, geen schema hier):
  - `admin_push_register {device_id, apns_token, platform, sandbox, app_build, prefs}`: controleert alles (`device_id` 8–80 tekens `[A-Za-z0-9_-]`, token hex 64–200, platform `ios`/`ipados`/`macos`, prefs precies vier booleans), haalt dezelfde token bij een ander `device_id` eerst weg en doet een upsert op `device_id`. Max. 30 per uur per IP.
  - `admin_push_unregister {device_id}`, `admin_push_prefs {device_id, prefs}` (404 `not_registered` als het apparaat er niet staat).
  - `admin_push_test {device_id}`: een testmelding naar alleen dat apparaat, **rechtstreeks via APNs** vanuit `admin` (ES256-JWT met WebCrypto uit `APNS_KEY_P8` / `APNS_KEY_ID` / `APNS_TEAM_ID`, HTTP/2 via Deno-fetch, sandbox- of productiehost per apparaat). Zonder die sleutels: 503 `apns_not_configured`; een ongeldige token wordt opgeruimd (410 `apns_invalid`). Max. 10 per uur per IP.
  - In `admin_audit` alleen de actie en het platform, nooit `device_id` of token. **Overal uitloggen** maakt `admin_push_devices` leeg.
- **App** (`ios/BingrBeheer/App/PushService.swift`): Push Notifications-entitlement (`aps-environment` = `development` in `project.yml`, op de Mac `com.apple.developer.aps-environment` in `BingrBeheer-macOS.entitlements`; bij archiveren voor TestFlight/App Store zet Xcode dat op `production`). Toestemming vraagt de app eenmalig een paar seconden na het inloggen (of via Instellingen), daarna `registerForRemoteNotifications` en `admin_push_register` (opnieuw bij een nieuwe token, build of omgeving; schakelaars via `admin_push_prefs`). De omgeving komt uit het ingebedde provisioning-profiel (`aps-environment`), anders DEBUG = sandbox. Platform: `ios`, `ipados` (iPad) of `macos` (Mac Catalyst). **Uitloggen** meldt het apparaat af (`admin_push_unregister`); verloopt alleen de sessie, dan blijven de meldingen aan tot je opnieuw inlogt. Meldingen verschijnen ook als de app open is (banner, geluid, berichtencentrum); een tik opent de `url` (ticket, Downloads of Status).
- **Instellingen → Pushmeldingen**: de systeemtoestemming (met *Meldingen toestaan*, of *Open systeeminstellingen* als hij geweigerd is), of het apparaat bij de server is aangemeld, schakelaars *Nieuwe tickets*, *Nieuwe antwoorden*, *Nieuwe builds* en *Statuswijzigingen*, en **Testmelding sturen**.
- **Eenmalig (eigenaar)**: in het Apple Developer-portaal bij de App ID `nl.lrvdlinden.bingr.beheer` de capability **Push Notifications** aanzetten (de APNs-sleutel `.p8` van het team werkt voor alle apps van het team, dus geen nieuwe sleutel nodig), daarna in Xcode bij *Signing & Capabilities* van **BingrBeheer** controleren dat *Push Notifications* er staat (automatisch ondertekenen maakt de profielen opnieuw aan, ook voor Mac Catalyst).
- Pushmeldingen van het beheer komen nooit in de changelog.

## Subdomein beheer.bingr.online instellen (eenmalig, bij de hoster)

1. Maak in het hostingpaneel (bij *Domeinen* / *Subdomeinen*) het subdomein **beheer.bingr.online** aan en laat het naar een **eigen map** wijzen, bij voorkeur buiten de webmap van bingr.online. Veel panelen maken zelf een map als `beheer.bingr.online` of `domains/bingr.online/beheer` aan.
2. Zoek op hoe die map heet vanaf de FTP-login (log in met een FTP-programma en kijk in de hoofdmap) en zet dat pad in het secret `FTP_DIR`. Let op: de huidige FTP-login komt direct uit in de webmap van bingr.online. Kan het subdomein alleen naar een map daarbinnen wijzen (bv. `beheer.bingr.online/`), dan is dat prima: `web/.htaccess` stuurt elke andere host (zoals bingr.online/beheer.bingr.online/) door naar https://beheer.bingr.online, en de workflow *Website* van bingr-website verwijdert die map niet (hij uploadt zonder `--delete`).
3. Staat de DNS niet bij de hoster zelf: maak een A-record (of CNAME naar bingr.online) voor `beheer` aan.
4. Vraag in het hostingpaneel een SSL-certificaat aan voor beheer.bingr.online (meestal *SSL / Let's Encrypt*, gratis). Zet, als het paneel dat kan, *HTTPS forceren* aan.
5. Start *Actions → Dashboard → Run workflow*. Bij een groen vinkje zonder waarschuwing staat het dashboard op https://beheer.bingr.online.

## GitHub Actions in een openbare repo

- De logs van elke run zijn openbaar: schrijf nooit secrets, interne adressen, FTP-mappen of gebruikersgegevens naar het log (GitHub maskeert secrets, maar niet wat ervan is afgeleid).
- Secrets gaan niet naar workflows van pull requests uit forks; de deploys draaien alleen bij een push naar `main` of handmatig.
- Elke `uses:` staat vast op een commit-SHA (met de tag erachter als commentaar); werk die bij door de SHA van de nieuwe tag op te zoeken (`git ls-remote https://github.com/<eigenaar>/<action> refs/tags/<tag>`, bij een geannoteerde tag de regel met `^{}`).
- Openbare repo's gebruiken geen betaalde Actions-minuten.
